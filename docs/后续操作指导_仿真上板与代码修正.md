### 3.3 RTL 出错时具体怎么查

1. 找日志中第一个 assertion、ERROR 或 mismatch，不从最后一行“仿真失败”猜原因。
2. 确认同一测试向量在原生 `smoke.exe` 中是否也失败。两者都失败优先查算法/描述字；只有 RTL 失败再查综合语义、存储依赖和 AXI。
3. 将失败缩小到一个操作码、一组输入，记录 `params[0:16]`、输入/输出偏移、形状、量化乘数和移位。
4. 查有符号性：RGB 原始字节按 uint8 解释，网络特征按 int8；累加按 int32，重标定乘法中间值按 int64。
5. 查边界：3×3 卷积零填充、高斯复制边界、形态学零边界、通道尾块、最后一个空间 tile。
6. 查舍入：正负数均为最近值、半值远离零；不能用对负数行为不同的右移代替既定规则。
7. 查地址和缓冲尺寸：测试平台 arena 为 8,388,608 字节、params 为 4,096 个 int32，与 HLS m_axi 仿真 depth 匹配。过去缩小 arena 导致过仿真 SIGSEGV，不能误当网络精度问题。
8. 修复后依次重跑原生测试、pytest、整网整数对照、HLS C/RTL。

需要看波形时，在**调试副本**的 Tcl 中将联合仿真命令改为 `cosim_design -rtl verilog -trace_level all`，重跑后从该 solution 的仿真目录打开波形。优先观察 `ap_start/ap_done`、描述字读取和 AXI 握手；`VALID=1 && READY=0` 是等待，不等于错误。等待是否永久不恢复需要结合时间和主从双方判断。波形可能很大，先用最小失败向量。

### 3.4 后续应补充的仿真覆盖

当前 RTL 向量主要是小尺寸算子测试。正式冻结前建议：

1. 在 `testbench.cpp` 中增加固定随机种子的 8/16/32 通道，以及不能整除并行度的通道尾块；覆盖 1×1 和 3×3 卷积。
2. 加入 int8 饱和、负半值舍入、concat 两种输入尺度、全空/全满/单像素/双域/孔洞/贴边掩膜。
3. 先用独立整数参考导出期望值，再让 C/RTL 测试比较逐元素差异；随机种子、向量哈希要留档。
4. 增加一张真实图的完整 25 层 RTL 顺序执行测试。可仿照 `ArenaBackend.infer()`，按 `model.json` 的描述字顺序调用核心；在每层完成时比较对应 CHW 字节。
5. 先估算整网 RTL 运行耗时，再扩大样本，不能把“一层通过”写成“整网 RTL 通过”。当前工程尚无完整整网 RTL 测试驱动，此项需要补写。

## 4. Vivado 整机重建、报告检查和下载文件发布

### 4.1 哪些情况下需要重建

- 只改界面文字、Python 调度：通常不重建 bitstream，但要做软件/交互回归。
- 只换兼容 ABI 的模型权重：通常不重建硬件，但需检查算子、维度、arena 容量及数值对照。
- 改 HLS 核心、并行度、接口、时钟、复位、AXI、视频层或约束：必须重新生成并验证 bit/hwh。

`configs/default.json` 中的硬件字段不是自动修改所有硬件的开关。当前 PIN/POUT/TILE 的实际定义在 `lesion_accel.cpp`；HLS 时钟在 `hardware/hls/build.tcl`；PS/FCLK 与视频连接在 Vivado Tcl；运行超时默认值在 `PynqBackend`。修改前应确认哪个文件真正被构建或执行。

### 4.4 时序失败的处理顺序

1. 保存失败报告，记录起点、终点、逻辑/布线延迟、时钟域和最差路径。
2. 先排除错误时钟定义、约束遗漏、跨域和复位问题。
3. 若仍是实际运算/地址路径：考虑增加流水级、降低组合地址计算深度、控制扇出或调整分块。
4. 对布线主导的小违例，可复用同版本的已布线工程运行 `hardware/vivado/resume_route.tcl`，它会执行当前 `finish.tcl` 的后布线优化和检查。
5. 改了硬件源码/连接后，不可拿旧 checkpoint 做恢复构建；必须重新综合。
6. 重新审查数值、资源和全部时序后再发布。当前 WNS 只有 +0.011 ns，任何改动都不保证仍通过。

## 5. 首次上板：准备和文件传输

### 5.1 物理连接

1. 关闭电源后确认板卡为 PYNQ-Z2，工程目标芯片为 `xc7z020clg400-1`。启动跳线 **JP1 设为 SD**；使用电脑 USB 供电时，电源跳线 **J9 设为 USB**，以板上丝印为准。
2. 将适配 PYNQ-Z2 的系统镜像写入 Micro SD 卡并插入板卡；当前以 PYNQ 3.1 系列为目标，启动后核对实际版本。工程文件随后单独复制，不是把 bit 文件写成系统镜像。
3. 用支持数据传输的 Micro USB 线连接电脑和板卡 **PROG/UART（J8）**，用于供电及串口通信。电脑 USB 供电是官方支持方式；本工程整板功耗尚未实测，不能以芯片估算功耗保证所有 USB 口均足够。优先直连电脑，使用短且可靠的数据线。
4. 显示器接板卡 **HDMI OUT**。多数电脑 HDMI 是输出口，不能直接接收板卡画面；若使用笔记本屏幕，需要另备 HDMI 采集设备。USB 鼠标或鼠标接收器接板卡 **USB Host**。
5. 准备一个可被 Windows 和板卡读取的 U 盘（优先已有 FAT32 U 盘，不要为此格式化有数据的磁盘）。USB Host 只有一个接口时，先插 U 盘复制文件并安全卸载，再换鼠标；需要同时连接可用兼容 USB Hub，并核对供电能力。
6. 本流程不接以太网、不设置板卡 IP。记录供电、SD、显示器、鼠标和线缆型号。

若改用 DC1 外接电源，断电后将 J9 设为 REG。官方规定输入为 7–15 V 直流、推荐 12 V，中心正极、插头内径 2.1 mm；使用明确适配板卡的稳压电源，核对完整插头尺寸及额定电流。12 V 不得接到 Micro USB。依据：[板卡手册第 3、4 节](https://dpoauwgwqsy2x.cloudfront.net/Download/PYNQ_Z2_User_Manual_v1.1.pdf)。

### 5.1.1 在 Windows 打开串口终端

1. 打开设备管理器 → “端口（COM 和 LPT）”，记录插入板卡后出现的 `USB Serial Port (COM9)`。COM 编号取实际值(9)，不照抄示例。没有 COM 口时先检查数据线、电脑接口和设备管理器驱动状态；若缺驱动，按板卡所用 FTDI USB-UART 安装对应 VCP 驱动。
2. 打开 PuTTY，连接类型选择 **Serial**，Serial line 填实际 COM 口，Speed 填 **115200**。在 Connection → Serial 中设置 **8 数据位、1 停止位、Parity=None、Flow control=None（115200 8N1）**。依据：[PYNQ 官方串口说明](https://pynq.readthedocs.io/en/v2.2.1/getting_started/terminal.html)。
3. 可在 PuTTY 的 Session → Logging 启用 All session output，把日志保存到 Windows 本次 `record/sessions` 目录。不要把密码或其他秘密粘贴进命令行日志。
4. 打开串口窗口，再给板卡开机；若板卡已启动，按 Enter 查看提示符。按系统实际账号登录；密码输入时不显示字符是正常现象。账号以镜像说明和你设置的凭据为准。
5. 看到 Linux shell 提示符后执行 `whoami`、`uname -a`、`python3 --version`，确认进入板端。后文所有 bash/Python 板端代码在此窗口执行，不是在 Windows PowerShell 执行。

只有一个程序能占用同一 COM 口。乱码先查波特率；完全没输出先查 COM 编号、数据线及板卡启动。多行代码分块粘贴，确认没有丢行后再继续。重新登录或重启后，重新执行第 5.3 节设置 BOARD_PY 和 PYTHONPATH。

正常 PYNQ 运行通过 `Overlay` 将 `.bit` 加载到 PL；这不是把 `.bit` 写成 SD 启动镜像。当前交付不含自启动 BOOT.BIN/独立裸机系统。首次不要另走 JTAG 加载不同设计，否则 Python 中的 HWH/驱动状态可能不匹配。

### 7.1 启动和正常操作

### 7.2 按表逐项验收

| 操作 | 预期结果 | 要保存的证据 |
|---|---|---|
| 同图调阈值、开闭、最大域、填洞 | 复用网络输出，重新后处理；显示 Network output reused | 参数和 timing 中 `network_reused` |
| 改 Alpha 或 View | 只重绘，不启动新推理 | 界面录像、frame_id 无无故增加 |
| 点击 Run | 同图也强制重新推理 | `network_reused=false` |
| 正在处理时连续换图、调参 10 次 | 最终只提交当前图片/参数对应结果；旧掩膜和指标不残留 | 录像、`record/events.jsonl`、最终 result.json |
| Reset | 恢复模型包冻结策略并重新推理 | 参数恢复；不要误以为只恢复 configs/default.json |
| 点击叠加图内病灶/背景 | 默认四宫格中选中状态正确，补边不误映射 | 横/竖图各一次录像 |
| 拔掉、重插鼠标 | 提示断开，恢复后可操作，无程序退出 | 日志和录像 |
| 无标注图片 | 显示 No ground truth / accuracy N/A | 保存图和结果 |
| 损坏 JPEG | 显示错误，当前有效结果清除；换到正常图可恢复 | 异常日志和后续正常结果 |
| 阈值 0 和 1 | 与整数参考一致；有效区以外不计面积 | 两端参数、掩膜和指标 |
| 空/退化掩膜 | 无除零崩溃，未定义指标显示 N/A/原因 | 结果 JSON |

无标注测试请复制一张图到单独测试目录并换成不对应任何标签的新文件名；不删除原标签。损坏文件也只在独立测试目录创建。

### 7.3 超时与恢复的专项验证

当前驱动每次核心调用默认等待 30 秒，超时后标记 poisoned，不再复用缓冲区。**界面 Reset 是算法/缓存重置，不是 FPGA 硬件复位，也不保证解除 AXI 卡死。**

建议先做软件故障注入：在测试中用假的 IP 对象令控制寄存器始终返回未完成，把 timeout 设为短时间，验证 `_start()` 抛 TimeoutError、poisoned 为真、下一次调用拒绝继续、`close()` 不释放仍可能被 DMA 使用的缓冲。再用假的 Pipeline 后端抛错，确认界面清除旧结果。此类测试当前需要新增，不能写成已通过。

真实板端发生超时时：

1. 记录当前层、描述字、最后操作和是否并行显示，保存日志。
2. 停止新任务；不要手动 freebuffer 后立即分配给其他用途。
3. 尝试正常退出应用；若无法确定 DMA 已停止，采用有序重启板卡，使 PL 和驱动状态一起复位。
4. 重新执行 ABI → 色条 → 单图对照，再恢复完整运行。
5. 只有定位为“合法但慢的计算”后才考虑调整超时，并记录单算子最坏耗时；不得用无限等待掩盖挂死。

不要通过在活跃 AXI 传输中随意断时钟、写随机寄存器或拔电来构造首轮故障测试。

## 8. 性能、公平比较和连续运行

### 8.1 基准命令

先退出其他占用 PL/HDMI 的程序。在板端选择实际存在的同一张图：

```bash
CASE="$(find data/demo -maxdepth 1 -name '*.jpg' | sort | head -n 1)"
test -n "$CASE" || exit 1
sudo env PYTHONPATH="$PYTHONPATH" "$BOARD_PY" scripts/benchmark.py --backend fpga --image "$CASE" --runs 100 --output record/benchmark_fpga.json
sudo env PYTHONPATH="$PYTHONPATH" "$BOARD_PY" scripts/benchmark.py --backend fpga --image "$CASE" --runs 100 --hdmi --output record/benchmark_fpga_hdmi.json
"$BOARD_PY" scripts/benchmark.py --backend fp32 --image "$CASE" --runs 100 --output record/benchmark_arm_fp32.json
"$BOARD_PY" scripts/benchmark.py --backend integer --image "$CASE" --runs 100 --output record/benchmark_arm_integer.json
```

整数软件参考可能很慢，先用 `--runs 1` 测速估算耗时，再做 100 次正式运行；1 次结果仅作预检。每个调用自带 3 次预热，每次重置缓存，避免把重复读缓存当推理。

当前脚本在导入 NumPy 前固定 BLAS 线程数为 1。`native` 后端依赖 Windows DLL，不能原样用作 ARM CPU 基线；板上用 `fp32` 和 `integer`。

### 8.2 计时含义和仍需补测的项

- `inference_ms` 包含后端预处理/调用/数据传输等开销，不是纯 MAC 或纯 PL 时钟周期。
- `postprocess_ms` 包含后处理及指标计算。
- `processing_ms` 到结果生成；`total_ms` 在 `--hdmi` 时还包含界面合成和帧提交。
- `throughput_fps` 按有效完成次数/统计区间计算；HDMI 提交时间不是显示器真正亮起的时间。
- 比较 CPU/FPGA 时必须同一板卡、同图、同模型、同策略、同计时边界。桌面 CPU 数字另列，不混入板上加速比。
- 当前 benchmark 没有独立统计“鼠标事件到新画面”的交互延迟。后续应在 `app.py` 中对事件、任务提交、结果完成、writeframe 前后加时间戳，至少统计 100 次；若要物理显示延迟，需要额外外部测量。
- 当前 benchmark JSON 不完整绑定 hardware_id、镜像版本和输入哈希，正式报告须另附这些字段或扩展脚本后补齐。

对比页可加载同模型的已有报告：

```bash
sudo env PYTHONPATH="$PYTHONPATH" "$BOARD_PY" -m lesion_fpga.app --backend fpga --images data/demo --report record/benchmark_fpga_hdmi.json
```

界面只展示报告中的部分标量字段，不会自动把全部资源表或多后端结果合成完整对比页。需要竞赛展示完整对比表时，另整理版本绑定的报告并扩展 `ui.py`，不要把未显示内容当已实现。

### 8.3 连续运行

建议先做至少 30 分钟交互循环：运行、切图、调参、保存、鼠标重连。另终端定期记录 `date`、`free -m`、`dmesg` 的相关错误；有可用温度传感器时记录其读数。随后按实际演示时长增加稳定性测试。

通过标准：无进程退出、持续黑屏、错帧、缓存泄漏趋势、AXI 超时；最后一张的参数/模型/掩膜/指标仍一致。一次未复现不能替代长期可靠性结论。

## 9. 常见问题的定位与修改入口

| 现象 | 首先做的检查 | 主要修改位置 | 修改后最小回归 |
|---|---|---|---|
| Model/hardware checksum mismatch | 文件是否混版、传输是否完整 | 模型包、hardware_manifest；不要删校验逻辑 | 重新发布校验、ABI、单图 |
| 没有 lesion_accel_0/video | bit/hwh 是否同目录同名；层级是否保留；视频驱动是否导入 | `hardware/vivado/build.tcl`、`backends.py` | 整机重建、ABI、色条 |
| 连续内存分配失败 | 其他 overlay/视频进程、CMA、内存占用 | 分配及生命周期；先停止多余进程 | 重启后的分配、100 次循环 |
| ABI 正常而卷积超时 | 描述字、指针、HP 连接、缓存同步、DDR 争用 | `backends.py`、HLS 核心、Vivado AXI 连接 | 最小算子 → 逐层 → HDMI 并发 |
| 首层即有差异 | RGB/CHW、uint8/int8、量化零点、预处理配置 | `imaging.py`、`quantization.py`、HLS preprocess | 输入张量及首层逐元素 |
| 某次 concat 后出现差异 | 两路尺度、顺序、偏移和舍入 | `export.py`、`quantization.py`、HLS concat | 分支输入及 concat 输出 |
| 网络相同但最终 mask 不同 | 阈值比较端点、开闭顺序、有效区、主域/填洞 | `pipeline.py`、`imaging.py`、HLS morphology | 边界掩膜、真实图最终对照 |
| 图像叠加错位 | letterbox 坐标、EXIF、原图回映射、鼠标坐标 | `imaging.py`、`ui.py` | 横/竖图、贴边、点选 |
| 黑屏/错色 | HDMI OUT、输入源、色条、PIXEL_RGB、同一 overlay | 视频层、`hdmi_colorbars.py`、`app.py` | 色条 → 单图 → 推理并发 |
| 操作后出现旧结果 | version 校验、pending 请求、异常清理 | `app.py`、`pipeline.py` | 连续切图/调参/错误恢复 |
| Windows 正常，板端 import 失败 | Python/ABI、root 环境、ARM 包；不要用 Windows DLL | 环境和依赖 | import → preflight → ABI |
| 无法复现某次结果 | 模型/图像/配置/硬件版本缺失 | 日志和结果元数据 | 用固定输入和参数重现 |

仅为调试查看 AXI 寄存器时，也要注意部分状态位具有读清除语义；不要在另一线程不断读控制寄存器，抢走驱动等待的完成状态。

## 10. 代码修正和算法升级流程

### 10.1 固定流程

1. 备份当前发布包和日志，记录现象与最小输入。
2. 定位第一个出错阶段，而不是直接修改最终阈值掩盖前级错误。
3. 为该缺陷添加独立期望值的回归用例。
4. 每次只改一个明确因素，记录文件、理由和影响范围。
5. 按下表完成回归；全部通过后再替换现场文件。

| 改动类型 | 必须执行 |
|---|---|
| 界面/鼠标/保存 | Python 测试、桌面 snapshot、板端交互表；无需无理由重训 |
| 坐标/后处理/形态指标 | 边界用例、最终掩膜/指标对照、验证/测试影响分析 |
| HLS 算术/并行度 | 重建 DLL、pytest、25 层对照、C/RTL、Vivado 全流程、板上逐层与性能 |
| AXI/寄存器/ABI | 同时修改模型/驱动/核心的协议版本和校验，重建 bit/hwh，重新做所有硬件检查 |
| 模型/输入尺寸/高斯 | 新训练与校准、内存预算、完整验证集策略选择、冻结后测试、整数/板端对照 |

不要直接编辑 `hardware/rtl_generated/*.v` 当长期修复；下一次 HLS 会覆盖。若确实引入手写 RTL，应作为独立源模块接入构建，写接口和独立测试平台，重新验证完整设计。

### 10.2 重训的具体做法

不改变模型时不要重训。需要新实验时复制配置为新文件、使用新 run 名，避免覆盖 baseline：

```powershell
Copy-Item configs\default.json configs\experiment_v2.json
# 此处编辑 experiment_v2.json，记录实际改动。
.\.venv\Scripts\python.exe -m lesion_fpga.train --config configs/experiment_v2.json --run experiment_v2
.\.venv\Scripts\python.exe -m lesion_fpga.export --checkpoint artifacts/checkpoints/experiment_v2/best.pt --output artifacts/models/experiment_v2
.\.venv\Scripts\python.exe scripts/compare_layers.py --model artifacts/models/experiment_v2
.\.venv\Scripts\python.exe -m lesion_fpga.evaluate --split validation --model artifacts/models/experiment_v2 --checkpoint artifacts/checkpoints/experiment_v2/best.pt
.\.venv\Scripts\python.exe -m lesion_fpga.evaluate --split test --model artifacts/models/experiment_v2 --checkpoint artifacts/checkpoints/experiment_v2/best.pt
```

评测结果仍写固定的 `artifacts/evaluation_validation.json`、`evaluation_test.json`，每次先备份并在结束后按模型 ID 归档。恢复同一次训练可加 `--resume`；配置必须与检查点一致。

验证集运行会写该模型目录的 `policy.json`，因此不要用 `--limit` 的试跑结果覆盖正式策略。测试集仅消费完整冻结策略，不能用于选阈值、训练或量化校准。

如果输入尺寸/高斯配置变化，先检查 `train.py`、`dataset.py` 的缓存建立逻辑和 `artifacts/cache` 文件是否匹配；不能复用旧预处理缓存。`configs/default.json` 的后处理默认值也不等于部署时的冻结 policy。

量化误差超过 1 个百分点时，先逐层排查尺度、饱和和校准覆盖，再设计 QAT。当前仓库没有“一键 QAT”入口，需补写训练流程后再验证，不能仅把导出名称改成 QAT。

### 10.3 当前脚本的限制，避免误用

- `compare_layers.py` 固定第一张验证图；多图覆盖需扩展样本选择参数和逐图输出，当前命令不支持凭空添加 `--image`。
- `evaluate.py` 顶层依赖 torch，且后处理评测使用软件函数。即便指定 `--backend fpga`，也不能直接当作无 PyTorch 的 ARM 全链验收程序。
- 完整板端测试集建议补一个轻量循环：读取冻结 policy 和 manifest，使用 `PynqBackend + Pipeline.run(..., ground_truth=...)`，保存逐图结果并按图平均 Dice/IoU；不在该脚本重新调参，不导入 torch。传输全部 376 张及标签后才做完整评测。
- `release_status.py` 当前把板上验收写成 pending，并读取固定日志路径；`hardware_manifest.json` 存在也不等于本轮重建成功。现场通过后需基于真实证据更新状态生成逻辑，不能靠重复运行自动转为通过。
- 现有 `finalize_hardware.py` 验证报告和文件一致性，但没有证明所有日志都来自同一轮。发布人员需核对时间、源文件哈希和本轮返回码，防止旧成功文件掩盖新失败。
- 256×256、INT4、CLAHE、去毛发和新摄像头输入均属于新版本，应独立预算与验证，不并入本轮验收结论。

## 11. 发布、回滚与最终检查清单

### 11.1 发布前

确认本轮 HLS/实现确实成功，最新报告已回收；不要只看到目录里有旧 `.bit` 就发布。先归档旧包，再在 Windows 执行：

```powershell
.\.venv\Scripts\python.exe scripts\finalize_hardware.py
if ($LASTEXITCODE -ne 0) { throw '硬件校验失败' }
.\.venv\Scripts\python.exe scripts\release_status.py
if ($LASTEXITCODE -ne 0) { throw '状态汇总失败' }
.\.venv\Scripts\python.exe scripts\package_release.py
if ($LASTEXITCODE -ne 0) { throw '打包失败' }
```

如果这次包含真实板上验收，先按第 10.3 节修改状态生成逻辑并引用证据，否则上述脚本仍会写 pending。不要把 `board_verified` 手动改为 true 而无对应记录。

`package_release.py` 会合并复制到现有 release，不能自动清除已删除的旧文件。文件集合改变时，先把旧 release 另存归档，再在一个空发布目录生成，避免遗留失效脚本。

重新复制到板端后重做第 5.3 节哈希校验、ABI 和一张图的快速回归。更换硬件时停止旧应用，确保 bit、hwh、hardware_manifest 三者一起更新；更换模型时整个模型目录和 policy 一起更新。

### 11.1.1 无网线取回板端日志和结果

停止当前 HDMI 应用后，再把鼠标换成 U 盘；如果没有其他退出方式，在运行应用的串口窗口按 Ctrl+C，等待程序退出。按第 5.2 节重新确认 U 盘并挂载，设置 USB_MOUNT。板端执行：

```bash
cd "$HOME/lesion_fpga"
RESULT_TAG=$(date +%Y%m%d_%H%M%S)
RESULT_DIR="$USB_MOUNT/lesion_results_$RESULT_TAG"
sudo mkdir -p "$RESULT_DIR"
sudo tar -czf "$RESULT_DIR/board_results.tar.gz" record artifacts
```

确认 tar 命令成功；U 盘空间须足够，FAT32 单文件不能达到 4 GiB，若结果过大应分批归档。该包包含日志、硬件/模型版本和生成结果，图像层数组也在 artifacts 中。检查归档，再安全卸载：

```bash
sudo tar -tzf "$RESULT_DIR/board_results.tar.gz" > /dev/null && echo 'Archive readable'
sync
sudo umount "$USB_MOUNT"
```

卸载成功后将 U 盘插回电脑，把 `lesion_results_时间` 目录复制到 Windows 工程的 `record/sessions/`，保留串口会话日志一起验收。关闭板卡前在串口执行 `sudo poweroff`，等待系统关机完成再断电。USB 同时供电时，不要用直接拔 Micro USB 代替正常关机。

### 11.2 回滚

1. 停止当前应用，保存故障日志。
2. 恢复同一历史版本的模型目录、bit/hwh/manifest 和对应软件，不能只换一个文件。
3. 如发生过 DMA/AXI 超时，先有序重启板卡。
4. 校验哈希，执行 ABI、色条和单图对照，确认恢复。
5. 在 record 说明回滚原因、恢复版本和复测结果。
